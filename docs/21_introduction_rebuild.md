# Introduction

Modern software systems increasingly depend on APIs not simply as technical connectors, but as the operational surface through which business logic is exposed, transactions are triggered, and system failures become visible. This is particularly true for transaction-heavy platforms, where defects in order processing, validation, pricing logic, access control, or state transitions can quickly move from a local software fault to a business-level problem. In such settings, the question is no longer whether testing is necessary. The more difficult question is what kind of testing method is defensible when the system is both API-centered and continuously changing.

That problem is easy to underestimate. Teams can have automated tests, CI pipelines, and even respectable coverage numbers, while still lacking a method that is coherent enough to justify why certain risks are tested more deeply than others, why several testing levels are needed, or why one metric should be trusted more than another. Put differently, automation by itself is not yet a methodology. A method only begins to emerge when test selection, test layering, execution logic, and evaluation criteria are organized around a clear quality rationale.

Recent literature points in that direction with surprising consistency, even if the papers do not prescribe one identical recipe. Research on REST API testing makes it clear that API behavior deserves explicit and systematic verification rather than indirect or purely incidental coverage (Ehsan et al., 2022). Work on automated black-box API testing shows that service interfaces can be meaningfully exercised without reducing QA to white-box internals alone (Martin-Lopez et al., 2021). Studies focused on nominal and error scenarios further reinforce that valid-path confirmation is not enough when robustness and failure behavior are part of the real quality profile of an API system (Corradini et al., 2022). Taken together, these studies do not offer a ready-made framework, but they do support the idea that QA for API-centric systems should be structured, layered, and sensitive to failure modes.

The same is true once delivery constraints are considered. Continuous integration environments make selective emphasis, reproducibility, and execution cost part of the testing problem rather than secondary operational concerns. Literature on continuous integration shows that CI changes testing discipline, feedback timing, and the way quality becomes visible during development (Soares et al., 2021). At the same time, work on test selection and prioritization suggests that not all tests provide equal value under continuous delivery conditions, and that informed selection is not a compromise but a legitimate testing strategy under practical constraints (Pan et al., 2021). This matters because a method that ignores uneven risk and uneven test value may remain broad in appearance while staying shallow in effect.

There is also a second issue that makes methodological clarity necessary: evaluation. Coverage remains common because it is easy to report and easy to compare, but it is also easy to overstate. On its own, coverage says little about whether the most meaningful faults are being revealed, whether a suite remains stable enough to trust, or whether the testing process stays usable inside CI/CD. Research on flaky tests is especially important here because it shifts attention from test presence to test credibility. If a suite behaves inconsistently, then even apparently strong automation can lose part of its evidential value (Parry et al., 2022). For that reason, a method-centered study of QA has to treat metrics as an analytical problem, not as a reporting ritual.

Against this background, the present paper does not treat one software project as the main research object. Its primary concern is the validity of a risk-informed, multi-level automated QA methodology for API-centric, transaction-heavy systems. The implemented e-commerce API case used in this study serves only as an empirical environment in which that methodology can be operationalized, observed, and evaluated. The purpose is therefore narrower and more disciplined than a project report: to examine whether the method can be justified from recent literature, whether it can be instantiated in a reproducible way, and whether the resulting evidence actually supports its practical value.

This distinction matters for the structure of the paper. The literature review is used to derive the methodological need rather than to decorate implementation choices after the fact. The method section defines the QA approach in abstract form before positioning the empirical case as a validation platform. The results section presents the evidence generated by applying the method, and the discussion evaluates what that evidence does and does not allow us to conclude about the method itself. In that sense, the paper is best understood not as a description of a repository, but as a literature-grounded technical study of QA methodology using a realistic API-based case.

From that starting point, the article is guided by the following research questions:

| ID | Research Question |
|---|---|
| RQ1 | What principles from recent literature justify a risk-informed, multi-level automated QA methodology for API-centric systems? |
| RQ2 | How can such a methodology be operationalized and evaluated in a reproducible empirical case? |
| RQ3 | To what extent do the observed metrics and defect patterns support the practical validity of the methodology in a transaction-heavy API context? |

These questions are designed to keep the paper method-centered from beginning to end. RQ1 anchors the study in the literature and prevents the argument from collapsing into local practice alone. RQ2 makes reproducibility and operational design central, which is important if the paper is to discuss a methodology rather than a loose set of engineering decisions. RQ3 ensures that the empirical case is used for what it should be used for: not to glorify the case itself, but to test whether the method produces credible evidence in a realistic environment. The broader aim is to show that a QA strategy based on risk awareness, layered automation, CI/CD execution, and multi-dimensional evaluation can be defended as a coherent method for similar API-centric systems, while also making clear where its evidential limits remain.

Keywords: software quality assurance, API testing, risk-informed testing, automated testing, continuous integration, test prioritization, flaky tests, transaction-heavy systems
